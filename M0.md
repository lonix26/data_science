# M0 — Modèle baseline : régression linéaire (5 variables)

Ce document décrit le notebook `Alain_M0.ipynb`.

## 1) Objectif et périmètre

Objectifs du **M0** :
- Entraîner un modèle **baseline** de **régression linéaire** pour prédire `SalePrice` (House Prices — Kaggle).
- Utiliser **uniquement** les 5 variables retenues lors de l’analyse exploratoire.
- Comparer **plusieurs stratégies de preprocessing** (imputation, encodage, scaling, log sur surfaces) **à modèle constant**.
- Sélectionner une configuration « gagnante » puis générer une **soumission Kaggle**.

Fichiers utilisés (dossier `Data/`) :
- `train.csv` : apprentissage + validation croisée.
- `test.csv` : prédictions finales (aucune vérité terrain disponible).
- `sample_submission.csv` : format de soumission Kaggle.

## 2) Variables utilisées

### Variables explicatives (5 features)
Liste des variables utilisées dans tout le notebook :

```python
features = ["OverallQual", "GrLivArea", "TotalBsmtSF", "AgeAtSale", "Neighborhood"]
```

- `OverallQual` : qualité globale (ordinal, numérique).
- `GrLivArea` : surface habitable hors sous-sol (numérique, continue).
- `TotalBsmtSF` : surface totale de sous-sol (numérique, continue).
- `AgeAtSale` : **feature engineering** (voir ci-dessous).
- `Neighborhood` : quartier (catégorielle nominale).

### Variable cible
- `SalePrice` (prix de vente).

## 3) Feature engineering

### `AgeAtSale`
Création d’une variable d’âge du bien au moment de la vente :

```python
AgeAtSale = YrSold - YearBuilt
```

Cette transformation est appliquée **à la fois** sur `train_df` et `test_df` pour garantir la cohérence.

## 4) Transformation de la cible (log)

Le modèle est entraîné sur la cible transformée :

```python
y_train_log = np.log1p(y_train)
```

Raisons principales :
- Le prix est fortement asymétrique (queue à droite). La transformation `log1p` rend la relation plus « linéaire ».
- Kaggle évalue généralement via une métrique de type **RMSLE** (erreur relative en log), qui est naturellement alignée avec un apprentissage en log.

Les prédictions sont ensuite ramenées à l’échelle du prix via :

```python
pred_price = np.expm1(pred_log)
```

Un **clipping à 0** est appliqué pour éviter des valeurs négatives dues à l’approximation linéaire.

## 5) Préprocessing (pipeline)

Le notebook utilise une **Pipeline scikit-learn** avec un `ColumnTransformer`, afin de :
- éviter les fuites de données (tout fit est fait **dans les folds** de CV),
- encapsuler imputation / transformation / encodage,
- rendre comparables plusieurs expériences.

### Groupes de colonnes
Les 5 variables sont séparées en 4 groupes, car la stratégie de traitement n’est pas la même :

- Numériques « classiques » (imputation médiane) :
  - `OverallQual`, `AgeAtSale`
- Surface (imputation médiane, option log) :
  - `GrLivArea`
- Surface « absence possible » (imputation à 0, option log) :
  - `TotalBsmtSF`
- Catégorielle (imputation + one-hot) :
  - `Neighborhood`

### Gestion des valeurs manquantes (NA)
Stratégie par défaut (la plupart des expériences) :
- `OverallQual`, `AgeAtSale`, `GrLivArea` : **imputation médiane**.
- `TotalBsmtSF` : **imputation constante à 0**.
  - Hypothèse métier : une valeur manquante correspond souvent à **absence de sous-sol**, donc une surface de 0 est plausible.
- `Neighborhood` : **imputation explicite** avec la modalité `"Missing"` (catégorie dédiée).
  - Cela permet de **tracer** les valeurs manquantes au lieu de les « masquer » en les remplaçant par le mode.

Alternative testée (une expérience) :
- `Neighborhood` imputé par le **mode** (stratégie `most_frequent`).

### Encodage
- `Neighborhood` est encodée via `OneHotEncoder(handle_unknown="ignore")`.
- Option d’expérience : `drop='first'` pour éviter la colinéarité parfaite (dummy variable trap).

### Transformations optionnelles par expérience
Selon la configuration :
- **Log sur les surfaces** (`GrLivArea`, `TotalBsmtSF`) via `FunctionTransformer(np.log1p)`.
- **Standardisation** des numériques via `StandardScaler()`.

## 6) Modèle

Modèle constant pour toutes les expériences :
- `LinearRegression()` (régression linéaire ordinaire, sans régularisation).

Le but du M0 est volontairement de rester sur un modèle simple et d’étudier l’impact du preprocessing.

## 7) Protocole d’évaluation (validation croisée)

### Cross-validation
- `KFold(n_splits=5, shuffle=True, random_state=42)`

La CV est strictement identique pour toutes les expériences afin d’assurer une comparaison **à armes égales**.

### Pourquoi faire la CV ici ?
- Éviter de sélectionner un preprocessing « chanceux » sur un seul split.
- Obtenir des estimations plus stables (moyenne + écart-type).

## 8) Expériences de preprocessing comparées

Chaque expérience change uniquement des paramètres de preprocessing. Les configurations sont :

- **E0_baseline** :
  - pas de scaling, pas de drop-first, pas de log sur surfaces,
  - `Neighborhood` NA → `"Missing"`.

- **E1_drop_first** :
  - identique E0, mais `OneHotEncoder(drop='first')`.

- **E2_scale_numeric** :
  - identique E0, mais standardisation des numériques.

- **E3_log_surfaces** :
  - identique E0, mais `log1p` sur `GrLivArea` et `TotalBsmtSF`.

- **E4_log_surfaces_scale** :
  - combine **log surfaces** + **scaling**.

- **E5_neighborhood_mode** :
  - identique E0, mais `Neighborhood` NA → **most frequent** (mode).

## 9) Métriques calculées

Le notebook calcule plusieurs métriques, pour refléter à la fois :
1) la logique Kaggle (erreur en log),
2) la logique métier « banque » (erreur en euros et risque de sur-prédiction).

### Métriques « Kaggle / log »
- `cv_rmse_log_mean` : RMSE entre `log1p(y_true)` et `y_pred_log`.
  - Interprétation : proche de la RMSLE Kaggle.

### Métriques « prix réel »
- `cv_mae_price_mean` : **MAE en euros** (erreur absolue moyenne).
- `cv_rmsle_price_mean` : RMSLE calculée sur les prix (via `log1p`).

### Indicateur de risque (banque)
- `cv_overpred_pct_mean` : **% de sur-prédictions** (cas où `prediction > réel`).
  - Intuition : une sur-prédiction peut représenter un risque (ex. financement trop optimiste).

## 10) Classements et choix du modèle « gagnant »

Le notebook construit 3 logiques de classement :

### (A) Classement Kaggle
Tri croissant sur :
1. `cv_rmse_log_mean`
2. `cv_rmse_log_std`

→ Produit `best_kaggle_config`.

### (B) Classement métier « banque »
Tri croissant sur :
1. `cv_mae_price_mean`
2. `cv_overpred_pct_mean`
3. `cv_rmsle_price_mean`

→ Produit `best_business_config`.

### (C) Décision globale pondérée (rang pondéré)
Le notebook calcule un rang global à partir des rangs, avec des poids :

```python
w_kaggle = 0.2
w_mae_business = 0.4
w_overpred_business = 0.6
```

- `rank_kaggle` : rang selon `cv_rmse_log_mean`
- `rank_business_mae` : rang selon `cv_mae_price_mean`
- `rank_business_overpred` : rang selon `cv_overpred_pct_mean`

Puis :

```python
rank_global_weighted = (
    w_kaggle * rank_kaggle
    + w_mae_business * rank_business_mae
    + w_overpred_business * rank_business_overpred
)
```

→ La configuration retenue est `best_global_config`.

Remarque : le notebook contient une note indiquant que ces pondérations peuvent être ajustées selon la priorité métier (ex. pénaliser encore plus la sur-prédiction).

## 11) Diagnostic visuel (out-of-fold)

Pour la configuration gagnante, le notebook produit :
- des prédictions **out-of-fold** sur le train (même CV),
- un nuage de points **réel (x)** vs **prédit (y)**,
- une diagonale `y=x` comme référence.

L’objectif est de détecter rapidement :
- biais systématique (sur/sous-estimation),
- hétéroscédasticité,
- outliers.

## 12) Entraînement final et soumission Kaggle

Une fois la meilleure configuration choisie :
1. Fit de la pipeline sur **tout `train.csv`** (toujours sur `y_train_log`).
2. Prédiction sur `test.csv`.
3. Transformation inverse `expm1`, clipping à 0.
4. Création du fichier de soumission :

```python
submission_m0_linear_{best_global_config}.csv
```

## 13) Limites connues (baseline)

- Modèle linéaire sans régularisation : sensible à la multicolinéarité et aux outliers.
- Seulement 5 variables : baseline volontairement simple.
- Le choix final dépend des poids métier/Kaggle : à documenter/figer selon le cadre du projet.

## 14) Reproductibilité

- Validation croisée déterministe via `random_state=42`.
- Les résultats peuvent légèrement varier selon l’environnement (versions de `numpy`, `pandas`, `scikit-learn`).
